1. Overview

Build a full sales pipeline into the PracticeRank admin dashboard. When a prospect runs a report on the landing page (or is manually added), they enter a kanban pipeline that tracks them from first outreach through signed contract and payment. The system auto-generates outreach emails from report data, tracks follow-ups, and closes deals through Stripe checkout.

2. Problem Statement

Right now, outreach is entirely manual. Jon or Ethan sees a report, manually writes an email, manually tracks who they've contacted, and has no system for follow-ups. Prospects fall through cracks. There's no visibility into the pipeline, no templates that pull real data, and no way to move someone from "interested" to "paying" without switching between multiple tools.

3. Goals & Success Criteria

  • Every landing page report automatically creates a prospect in the pipeline
  • Outreach emails auto-populate with real report data (scores, findings, competitor gaps)
  • Kanban board with drag-and-drop stages visible on the dashboard
  • Email templates follow Hormozi-style best practices (lead with pain, specific data, risk-free CTA)
  • Stripe integration for prospect self-checkout when they're ready to sign up
  • Activity log per prospect (emails sent, calls logged, notes)
  • Follow-up reminders so nobody falls through the cracks

4.2 Outreach Email Best Practices (Hormozi Framework)

All email templates follow these rules:

  • Open with their data, not a compliment. Lead with a specific finding from their report (score, competitor gap, missing AI visibility)
  • Quantify the gap. Use real scores and competitor comparisons from the audit. Never fabricate numbers we don't have
  • Name the problem they didn't know they had. AI search visibility is new enough that most firms don't know they're invisible
  • Show what we do in one paragraph. AI discoverability, SEO, review automation, schema markup. Concrete, not vague
  • Risk-free CTA. Ask for a 15-minute call, not a commitment. "What does your calendar look like this week?"
  • No fabricated metrics. Only use data from the actual report. No "estimated inquiries/mo" or revenue projections
  • Short. Under 250 words for initial outreach. Every sentence earns its place
  • No dashes. Rewrite sentences that rely on em dashes
  • Vertical-aware language. "Firm" for legal, "practice" for dental/medical, "company" for tech. Never cross terminology

4.5 Rules & Constraints

  • Prospects with email = null cannot have outreach sent (show warning)
  • Never auto-send emails. Always preview first, human clicks "Send"
  • Landing page reports auto-create prospects ONLY if the user provided an email
  • Lost prospects can be re-opened (moved back to Follow-up) with a note
  • When a prospect reaches "Customer" stage, auto-create a customer record in the existing customers table
  • All email content is stored in the activity log for audit trail

4.6 Edge Cases

  • Same domain runs multiple reports: update existing prospect, don't create duplicate
  • Prospect already exists as customer: show "Already a customer" badge, skip pipeline
  • Report has no Google data (blocked site): still create prospect but flag "Limited data" on outreach template
  • Multiple people at same firm submit reports: merge by domain, keep all contact emails

5. Technical Design

5.1 Architecture

Everything lives in the existing Flask dashboard. New prospects and prospect_activities tables in SQLite. Kanban board as a new top-level tab. Email templates stored as Jinja2 files in templates/emails/outreach/. Stripe integration via Checkout Sessions API (server-side, no Stripe.js needed).

5.4 Database Changes

CREATE TABLE prospects (
    id TEXT PRIMARY KEY,
    domain TEXT NOT NULL UNIQUE,
    name TEXT NOT NULL,
    email TEXT,
    phone TEXT,
    contact_name TEXT,
    vertical TEXT DEFAULT 'dental',
    stage TEXT DEFAULT 'new_lead',
    lost_reason TEXT,
    report_id TEXT,
    overall_score INTEGER,
    grade TEXT,
    report_data TEXT,              -- full report JSON for template rendering
    stripe_checkout_id TEXT,
    stripe_customer_id TEXT,
    notes TEXT,
    created_at TEXT NOT NULL DEFAULT (datetime('now')),
    updated_at TEXT NOT NULL DEFAULT (datetime('now')),
    FOREIGN KEY (report_id) REFERENCES landing_page_reports(id)
);

CREATE INDEX idx_prospects_stage ON prospects(stage);
CREATE INDEX idx_prospects_domain ON prospects(domain);

CREATE TABLE prospect_activities (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    prospect_id TEXT NOT NULL,
    activity_type TEXT NOT NULL,   -- 'email_sent', 'call_logged', 'note', 'stage_change', 'stripe_event'
    stage_from TEXT,
    stage_to TEXT,
    subject TEXT,                  -- email subject or activity title
    body TEXT,                     -- email body or note content
    created_by TEXT,               -- dashboard user who performed action
    created_at TEXT NOT NULL DEFAULT (datetime('now')),
    FOREIGN KEY (prospect_id) REFERENCES prospects(id)
);

CREATE INDEX idx_activities_prospect ON prospect_activities(prospect_id);
CREATE INDEX idx_activities_type ON prospect_activities(activity_type);

5.5 Stripe Integration

  • Use Stripe Checkout Sessions (server-side) to generate payment links per prospect
  • Products/prices pre-created in Stripe dashboard for each tier (Starter, Growth, Premium)
  • Webhook endpoint at /api/stripe/webhook listens for checkout.session.completed
  • On payment success: move prospect to "Customer" stage, auto-create customer record, log activity
  • Env vars: STRIPE_SECRET_KEY, STRIPE_WEBHOOK_SECRET, STRIPE_PRICE_STARTER, STRIPE_PRICE_GROWTH, STRIPE_PRICE_PREMIUM

6. Security Considerations

  • Stripe webhook signature verification (stripe.Webhook.construct_event) on every webhook call
  • All prospect routes require @login_required
  • Email body sanitized before storage (no raw HTML injection)
  • Stripe secret key and webhook secret in env vars only, never in code or templates
  • Rate limit prospect creation from landing page (already handled by worker rate limiting)
  • Prospect email addresses not exposed in client-side JavaScript
Security checklist: Input validation on all prospect fields, auth on all routes, SQL parameterization (already using sqlite3 params), no Stripe keys in frontend, webhook signature verification.

8. Testing Plan

8.1 Manual Verification

  • Run a report on the landing page with an email, verify prospect auto-created in pipeline
  • Open prospect detail, verify report data populates email template correctly
  • Drag prospect between kanban stages, verify activity log records the transition
  • Preview outreach email, verify all template variables are filled with real data (no {{placeholders}} visible)
  • Generate Stripe checkout link, complete test payment, verify prospect moves to Customer stage
  • Verify legal prospects get "firm" language, dental get "practice" language in templates
  • Test duplicate domain handling: second report for same domain updates existing prospect
  • Test lost prospect re-open flow

9. Risks & Rollback

  • Stripe webhook reliability: use idempotency keys and retry logic. Log all webhook events
  • Email deliverability: initially emails are generated in the dashboard for manual copy/paste send (not SMTP). Phase 2 can add SendGrid/Resend for actual sending
  • Large prospect volume: SQLite handles this fine at current scale. If 10K+ prospects, consider pagination

Rollback Plan

New tables and routes only. No existing tables modified. Remove nav link and routes to fully rollback. Stripe products can stay in dashboard without harm.
