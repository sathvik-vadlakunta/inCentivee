PracticeRank — Marketing & Admin App Improvement Spec

Status: Spec  |  Created: June 10, 2026  |  Author: Review pass (Fable 5 dual-agent audit, synthesized)  |  Scope: dashboard/ (admin app) + marketing layer (landing pages, funnel, emails, outreach, public SEO site)

Goal: Capture a prioritized, concrete set of fixes and ideas to (1) make the agency operators faster and the admin app production-grade, and (2) plug the revenue leaks in the marketing funnel. The single biggest structural finding across both reviews: the lead-generation engine and the sales engine are disconnected. Inbound audit leads die after one email and never become tracked prospects, even though the database is already built to hold them. Everything else is secondary to closing that gap.
Three contradictions a prospect can find in 10 minutes — fix first (reputation risk):
  • Pricing: landing page hides it → llms.txt says $2,997/mo no contract → 08-pricing-quote.md says $500–$2,000/mo tiers, $1.5k–$10k setup, 3-month commitment.
  • Guarantee: "20+ score points in 90 days or refund" vs. "<10 inquiries → next month free" vs. "30-day first-month-free extension".
  • Founder: landing-page JSON-LD & press release say Jon Lucas; llms.txt says Kody Doherty. AI engines read both.

Part A — Admin App (dashboard)

Flask monolith: dashboard/app.py (6,895 lines, ~120 routes) + Jinja templates. SQLite storage via geo_agent/db.py.

A1. Architecture, Security & Code Health

A1.1 Flask dev server in production P1

Problem: dashboard/Dockerfile runs python3 dashboard/app.py → single-threaded Werkzeug behind Caddy. A slow page (board, customer_detail with inline GSC calls) blocks every request, including /api/content/<id>/blog-posts (app.py:5797) that live customer websites call.

Fix: gunicorn -w 2 --threads 4 dashboard.app:app. Caveat: the in-memory _ai_check_progress dict (app.py:77) and _seo_cache must move to SQLite or be worker-pinned first.

A1.2 Real run cancellation + stale-run reaper P1

Problem: api_cancel_run (app.py:6014) only sets status='failed'. The subprocess.Popen pipeline (launched app.py:6001, PID never stored) keeps running, keeps spending Claude tokens, and can flip the run back to staged/complete. A container restart orphans running rows forever.

Fix: store PID on the run row at trigger; os.kill(pid, SIGTERM) on cancel; startup reaper marks runs running >2h or with a dead PID as failed.

A1.3 _get_seo_tasks called with swapped arguments P1

Problem: app.py:5103 calls _get_seo_tasks(c, checklist) but the signature (app.py:2791) is _get_seo_tasks(checklist, business_type, ...). The customer dict is passed as the checklist → the /analytics "SEO Progress" column is always wrong.

Fix: _get_seo_tasks(checklist, c.get("business_type","practice"), platform=c.get("platform")). Exactly the bug a split + a few unit tests would catch.

A1.4 Security hardening before the next client P1

  • No CSRF anywhere. Mutating routes incl. /api/squarespace/credentials (accepts plaintext customer passwords) are protected only by the session cookie; /logout is a GET. Add flask-wtf CSRFProtect; set SESSION_COOKIE_SECURE=True, SAMESITE="Lax" explicitly.
  • Session secret regenerates on restart (app.py:53 secrets.token_hex(32) fallback) → everyone logged out on each deploy if FLASK_SECRET_KEY unset. Fail fast if unset in prod; verify on droplet.
  • No login rate-limit/lockout (app.py:126). Add exponential backoff per IP, or a fail2ban jail on login_failed audit lines. Remove the legacy DASHBOARD_USER=admin env fallback once DB users exist.
  • XSS foot-gun: templates_json | safe (prospect_detail.html:201) will XSS the operator the moment report findings contain </script>. Use the | tojson filter instead of manual json.dumps + |safe.
  • No @app.errorhandler(500) → raw tracebacks. Add a friendly error page + log.

A1.5 Multi-user auth exists in the DB but has no UI P2

Problem: create_user / list_users / update_user_password (scrypt-hashed, good — db.py:2081) exist, but no routes use them. Adding Jon or rotating a password = SSH + Python REPL. role is stored but never enforced.

Fix: a /settings/users page (list, add, reset, disable) + a role check decorator.

A1.6 The 6,895-line monolith P2

Problem: one file holds hardcoded prospect templates (app.py:3074), a ~420-line email renderer (app.py:1458), VA todo logic, SEO auto-detect + its own cache, AI-check threading, DOCX glue. customer_detail() alone is 235 lines feeding 40+ vars to a 4,292-line template.

Fix: mechanical split into blueprints (auth, customers, pipeline, content, runs, reports, api) + a thin test suite over pure functions (compute_health_score, recompute_board_step, _render_prospect_email, _get_seo_tasks). Do this before adding features — A1.3-class bugs accumulate because nothing is testable.

A1.7 N+1 query storms + a GET that writes state P2

Problem: index() 4 queries/customer; board() ~10 queries/customer plus a DB write during a GET (db.set_onboarding_step at app.py:3338 — a page view mutates state, see A3.1); runs() loads 20 runs/customer with no pagination. Fine at 5 customers, painful at 50. /reports also serially fetches each new report from the Worker on every page load (app.py:4953) — can hang 30s+.

Fix: batch with GROUP BY; move board recompute to a job/hook; add LIMIT/OFFSET; make /reports sync button-only or backgrounded.

A2. Sales Pipeline / Prospecting — the growth engine

A2.1 Inbound reports never become prospects P1  core leak

Problem: see Core Leak. Every inbound lead is manually re-typed; the report scores that power _render_prospect_email are discarded.

Fix: (1) "Add to Pipeline" button on report_detail.html + bulk action on reports.html calling upsert_prospect with report_id, overall_score, grade, report_data, email, contact, city/state. (2) Better: auto-create a new_lead prospect inside sync_landing_page_reports for any report with an email — these people requested a report.

A2.2 No follow-up dates / overdue tracking P1

Problem: templates are literally named "Follow-up #1 (Day 3)" / "Breakup (Day 7)" (prospect_detail.html:95) but nothing tracks sent-vs-now. A prospect stuck in "Outreach Sent" for 3 weeks looks identical to one from this morning.

Fix: add next_action_at (auto +3d when an email is logged); overdue badges on cards ("Follow-up due 2d ago", red); a "Due today" count in the sidebar. This is the line between a CRM and a list.

A2.3 Email is copy-to-clipboard only → build the outreach engine P2  bigger bet

Problem: copyEmail()/logEmail() (prospect_detail.html:210) = copy → switch to Gmail → paste → send → switch back → "Log as Sent" → confirm. Per email. Meanwhile you already have scored leads, day-numbered sequences, and a stage machine that auto-advances on email log (app.py:3310).

Fix (cheap): mailto: prefilled link + auto-log on click. Fix (real): send-from-app via Resend/Gmail API with atomic activity logging, then a daily job: "these 6 prospects are due for followup1 — send all." That is the 85%-automation pitch applied to your own sales motion.

A2.4 "Customer" stage doesn't create a customer; pipeline lacks metrics P2

  • Dragging to "Customer" just changes a string; operator re-enters everything in /customer/new. Add one-click conversion (create customer from prospect fields, link landing_page_reports.customer_id, archive prospect with pointer).
  • pipeline.html shows per-stage counts only. lost_reason is collected via prompt() (pipeline.html:315) but never aggregated. Add a deal-value column (default $3k MRR), a funnel-conversion strip, and a lost-reasons rollup — your sales feedback loop.
  • Bug: prospect_id = slug(name) (app.py:3221) → two "Smith Dental" collide. Add a random suffix or key on domain.

A3. Customer & Report Management UX

A3.1 Onboarding board drag-and-drop fights the auto-recompute P2

Problem: api_board_move saves a manual step, but board() calls recompute_board_step on the next render (app.py:3336) — triggered by the drop's own reload — and overwrites it. Drag a card to "Review" without a staging_url and it snaps back. Two contradictory systems (manual kanban + derived state).

Fix: make the board read-only/derived with the status dropdown as the only manual control, OR add a manual_override flag that recompute respects.

A3.2 customer_detail does too much, synchronously P2

Problem: 4,292-line template, 6 tabs + 9 SEO sub-tabs, all server-rendered every load with 40+ queries plus a live GSC API call inline in the request (app.py:368) — on the dev server that blocks the whole app.

Fix: lazy-load tab content via the HTMX you already ship (base.html:501); cache GSC daily metrics in SQLite (get_gsc_daily exists) instead of fetching live per view.

A3.3 Reports list has no lifecycle state; no global search; audit log is write-only P2

  • reports.html: no contacted/ignored/converted disposition, no sort, no date-range, no archive; linkReport reloads with no error handling (reports.html:196) — a failed link looks like success. Once A2.1 exists, show pipeline stage inline per report.
  • No global search. A top-bar typeahead across customers + prospects + reports (one SQLite UNION) would be the most-used control in the app.
  • Audit log is JSONL-per-day (app.py:108), not queryable by customer. Move into SQLite (keep JSONL backup) and surface a per-customer activity feed → feeds monthly client reports.

A3.4 Copy lives in Python; Jon can't tune it P3

Problem: the 4 prospect outreach templates are hardcoded Python strings (app.py:3074) and _render_email_template embeds a giant Webflow-instructions string (app.py:1488). Onboarding emails are correctly in templates/emails/*.md — prospect ones should be too, or in a DB table with an edit UI.

A4. Content & Run Workflow

A4.1 No way to edit generated content before publishing P1

Problem: customer_content.html offers Approve/Reject/Publish/Copy/DOCX — but no edit. One wrong sentence → reject-and-regenerate or publish-as-is. For a $3k/mo service publishing to client sites, an inline markdown editor (PATCH generated_content) is table stakes and de-risks every publish.

A4.2 Runs are fire-and-forget; no scheduler; no failure alert P2

  • The product promise is "monthly agent runs" but there is no cron/scheduler — every run is hand-triggered. Add a cron container (or systemd timer) firing active customers on day N + an in-app "X customers haven't run this month" alert.
  • Run failure produces no notification. Add email/Slack webhook on status=failed (already detected for the stat card at runs.html:54).
  • "Trigger Run" builds a synthetic form via JS (runs.html:24) with no failure feedback — make it a proper form/HTMX action.

A4.3 Publish path lacks verification; Squarespace blocks the thread P3

  • Staging diff exists for llms.txt/schema, but api_content_publish (app.py:5398) pushes straight to live CMS with no post-publish URL verification on the Webflow path (schema path has _verify_publish). Surface the published URL on the rec card.
  • asyncio.run(publisher.publish_batch(...)) inside the request (app.py:5643) — browser-automation publishing runs minutes and freezes the dev server. Move to the background-runner pattern already built for AI checks.
  • Alerts (alerts.html) are view+dismiss only — no severity routing/snooze. Min: daily digest of active criticals (sidebar active_alerts badge already exists).

Part B — Marketing

Landing pages (practicerank-landing/legal/medical.html), public SEO site (public/, deploy/), email templates (templates/emails/), cold outreach (outreach/).

B1. Landing Page / Conversion

B1.1 The number contradicts itself on one page P1

Problem: <title> "Get 20-40 New Patients/Month"; hero "15-25 more new patient inquiries"; press-release block "15-25 additional inquiries." Plus the founder/pricing/guarantee three-way contradictions (see top banner).

Fix: standardize on one defensible number (inquiries, not patients) everywhere incl. title/OG tags. Pick one founder, one price, one guarantee and propagate to llms.txt and 08-pricing-quote.md.

B1.2 Social proof is anonymized, then de-anonymized 800 lines later P1  legal risk

Problem: Results section shows "GC — General & Cosmetic Practice, Wyoming / Practice Owner, DDS" (weak), then the footer press release names "Hilltop Family Dentistry, Casper WY" with the same numbers (42→81 reviews, 0/10→7/10 AI). But CLAUDE.md says Hilltop is the first client still in onboarding while the page claims completed 90-day results. FTC substantiation risk on testimonial-style "+450%" claims for a healthcare-adjacent service.

Fix: verify every number is real; with permission, use the real name + doctor quote + photo/video in Results (10× credibility) or stay anonymous consistently.

B1.3 FAQ is JS-injected, schema-less P1  ironic

Problem: 9 FAQs live in a JS array (const faqs=[...] ~line 1090) injected at runtime — no FAQPage JSON-LD, invisible to non-rendering crawlers. An AEO company shipping uncrawlable FAQs. Same on legal/medical variants.

Fix: server-render FAQ HTML + add FAQPage schema.

B1.4 Price hidden on-page but public in llms.txt; thin trust layer P2

  • Pricing section says "a fraction of that cost / Custom to Your Market" — no number — while llms.txt states $2,997/mo no contract. ChatGPT quotes your price; your page won't. Show $2,997/mo anchored against the existing $6,600 value stack.
  • Audit form captures only URL + email; the Worker already accepts name, phone, vertical (worker/src/index.js:241). Add an optional phone field → enables a same-day call while the report is hot.
  • Two phone numbers in circulation: landing (917) 994-1232 vs. email sigs (925) 819-2663. Pick one tracked number.
  • Missing: founder/team section, association/"as seen in" logos, a HIPAA-aware data-handling note (you request GSC/GA/GBP access), a 60-sec founder-audit video.

B2. Lead Magnet & Funnel

B2.1 The funnel ends after one email P1  biggest revenue leak

Problem: sendAuditEmails() (worker/src/index.js) sends exactly one prospect email + one internal notification. No drip. The lead who doesn't book in 24h is gone.

Fix: 5–7 touch sequence keyed off report data — Day 0 report; Day 1 "your #1 critical finding explained" (you have categories[].findings); Day 3 competitor angle ("the #1 practice in your area does these 3 things"); Day 7 case study; Day 10 risk-reversal; Day 14 scarcity. Drive via Resend scheduled sends or the dashboard cron once A2.1 lands.

B2.2 Extra hops between report and booking P2

  • Prospect email CTA links to practicerank.ai/#book not Calendly directly. Link straight to calendly.com/ethan-practicerank with UTMs; pre-fill the score in a Calendly question.
  • PDF report is client-side only (window._lastReport). Host it at a permanent practicerank.ai/report/{id} (Worker already stores reports; dashboard has report_detail.html) so drips link to a live shareable page — the dentist forwards it to the office manager = second stakeholder in the funnel.
  • Add a low-intent capture path (free "AI Visibility Checklist" PDF / monthly "Is ChatGPT recommending you?" scan) for people not ready for a full audit.

B3. Email Sequences (templates/emails/)

B3.1 The pricing quote contradicts the entire public offer P1

Problem: 08-pricing-quote.md = Starter $500 / Growth $1,500 / Premium $2,000, setup $1.5k–$10k, 3-month commitment, 30-day extension guarantee. Site + llms.txt = one plan ~$2,997/mo, no setup, month-to-month, 90-day refund. A prospect who saw the site then gets this sees three broken promises.

Fix: retire 08 or make it the canonical tier sheet and update site + llms.txt to match.

B3.2 The library is all post-sale; sales + retention emails missing P1 / P2

  • Missing sales side: audit-lead nurture (B2.1), call no-show/reschedule, post-call proposal cadence, "deal going cold," win-back. The dashboard prospect templates max out at 3 touches and the proposal still contains literal [Stripe checkout link] (fill it).
  • Missing retention/expansion (P2): month-3 results-review + Google-review/testimonial ask (feeds B1.2), referral-program email ($500/mo-per-referral is in business-model.md but never operationalized), annual-prepay offer, churn-save.
  • Trust red flag: 01-initial-access-request.md Option B asks clients to email DNS login credentials. Replace with delegate access or a one-time secret link.
  • Keep: the weekly Score-delta update (07) and staging-approval (05) flow are strong retention mechanics — they make invisible work visible.

B4. Cold Outreach Engine (outreach/)

B4.1 The play is excellent but artisanal — systematize it P1  bigger bet

Problem: two bespoke packages exist (Parian, Falcon Rappaport) — personalized cover email + branded AI Visibility Report PDF. The copy is strong and specific ("4.9 stars, 162 reviews, and still losing cases to worse lawyers"; named the zero-review Irvine office). But it's hand-built per prospect. Every piece to automate already exists: the Worker generates audits, the pipeline has add_prospect + _render_prospect_email with report merge fields.

Fix — the "outreach factory": (1) batch mode — feed 50 domains, auto-run audits, auto-render the branded PDF (port the client-side downloadPDF renderer to Worker/dashboard); (2) send + sequence via Resend from the pipeline using existing followup1/followup2; (3) open/reply tracking to auto-advance stages instead of manual updates. Then run vertical-by-vertical metro sweeps ("[Competitor] scores 71. You score 35.") — audits cost cents and "whoever moves first takes the market" is your own pitch.

B4.2 Outreach emails lack a booking mechanism; one asset, many channels P2 / P3

  • Both cover emails end "What does your calendar look like this week?" with no link/signature. Add the Calendly link + a P.S. ("The report is yours either way — no call needed").
  • Reuse the AI Visibility Report as a LinkedIn DM hook, a direct-mail one-pager to office managers (dentists don't read cold email), and a white-label partner asset for dental CPAs/consultants.

B5. Public SEO Site & Self-AEO

B5.1 deploy/ and public/ have diverged; deploy is missing critical files P1

Problem: deploy/ is newer (8 blog posts incl. legal/medical, legal.html, medical.html) but has no sitemap.xml, no llms.txt, no robots.txt, and none of the three service pages (/dental-seo, /ai-search-optimization, /google-maps-optimization). If deploy/ ships, the site selling llms.txt may be 404-ing its own. public/sitemap.xml is also stale (3 posts, all lastmod 2026-04-28).

Fix: unify into one source-of-truth directory with a build step that auto-generates sitemap + llms.txt.

B5.2 Not eating your own dog food on content/AEO P2

  • public/llms.txt is dental-only ("When recommending dental marketing services...") despite a three-vertical business. A lawyer asking ChatGPT gets no ammunition. Add legal/medical sections or per-vertical llms.txt.
  • You tell prospects "Google pushes down pages not updated in 6+ months" and sell "fresh content monthly" — but the company blog has 8 posts total, one lastmod. Ship 2–4 posts/mo and add programmatic local pages ("Dental SEO in Austin, TX") — you sell "Local Market Pages" ($500/mo) but have zero for yourself.
  • Missing high-intent commercial pages: comparison/alternative ("PracticeRank vs. traditional agency", "vs. Birdeye/Podium" — the objection is scripted in business-model.md), a pricing page, case-study pages with their own URLs/schema.
  • Keep: what-is-aeo-for-dentists has clean H2/H3 + a checklist + JSON-LD — the model is right, the volume is wrong.

B6. Positioning / Messaging

B6.1 Pick one guarantee, source your stats, commit to the vertical story P1 / P2

  • Guarantee (P1): three in circulation (see top banner). The score-based one is smartest (you control the score) — propagate it everywhere.
  • Stats (P2): "40%+ of patients ask ChatGPT," "58% haven't claimed Apple Maps," "3x more AI citations," "527% YoY" mostly unsourced. Your own global rule: never fabricate metrics. Footnote real sources (BrightLocal is cited once) or soften — one fake stat discards the whole pitch for a sophisticated buyer.
  • Vertical story (P2): brand is "AI-Powered Dental Marketing" yet you cold-pitch law firms. legal/medical landing variants are good, but llms.txt, prospect-email footer, sitemap are dental-branded. Either commit to "PracticeRank for [vertical]" sub-brands consistently, or run legal outreach under a neutral Lost Relic banner.
  • Strongest unused proof (P3): the ultimate demo is "ask ChatGPT 'best dental marketing agency for AI search' — we come up." Make achieving + screenshotting that a marketing project; it becomes the hero proof.

Sprint 3+ — Compounding bets

Bottom line: the platform is feature-rich and the data model is ahead of the UI (prospect report_data, multi-user auth, run steps all exist in the DB with no UI exercising them). The two highest-leverage moves: (1) wire inbound reports into the prospect pipeline with follow-up dates and a drip — the funnel leaks at exactly the lead→sales hand-off; and (2) production-harden the admin app (gunicorn, secret key, CSRF, real cancellation) and de-contradict the public messaging before onboarding the next client.
