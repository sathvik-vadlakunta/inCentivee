# Google Business Profile (GBP) Monthly Management — automation + Dan's ops loop

**Status:** active (spec / not yet implemented)
**Created:** 2026-06-26
**Owner:** Kody
**Trigger:** Paradigm's prior SEO team did monthly GBP updates. GBP is the single biggest
local-pack lever (prominence + activity + relevance), we already promise "Google Business
Profile management," and onboarding already collects **GBP Manager access** — but we don't yet
use it. This spec turns monthly GBP maintenance into a mostly-automated `geo_agent` job with a
tight human-approval loop for Dan and a customer email campaign for the parts only the client can do.

## Goal

Every active customer gets, every month: a fresh GBP **post**, **photos**, **review replies**,
a **Q&A check**, **info-accuracy check**, and a **performance pull** — generated by our content
engine, gated by the same guardrails as on-site content (`validate_html_claims`), and pushed via
the Google Business Profile API where the API allows. Where the API no longer allows it (Q&A), it
becomes a Dan checklist item + a customer email reminder.

Approval is **two-stage and reusable**: **Dan QA first** (internal quality gate on every item),
then an **optional login-free client approval portal** (modeled on the weekly report link) that
covers **all** monthly change types — blog posts, content edits, GBP posts/photos, review replies —
for clients who want to sign off. See "Two-stage approval" below; it's the robust core, not GBP-only.

## Background — what changes monthly + the value (research 2026-06-26)

| Item | What | Value | Automatable? |
|---|---|---|---|
| **Post** (What's New/Offer/Event) | 1+/mo, keyword-rich + CTA | Freshness "tiebreaker"; impressions drop after ~30 days idle | ✅ API |
| **Photos** | 3–5/mo, geo-tagged | +42% direction requests, +35% site clicks; photo engagement is a ranking input | ✅ API |
| **Review replies** | Respond to new reviews | Response rate/recency = ranking + trust | ✅ API (read+reply), human-approve |
| **Q&A** | Seed + monitor owner Q&A | Trust + keyword content | ❌ **API discontinued 2025-11-03** → manual |
| **Info accuracy** | Hours (holiday/seasonal), services, attributes, description, products | Relevance; prevents NAP suppression | ✅ Business Information API |
| **Performance pull** | searches, calls, directions, views | The monthly report + replaces Places-only estimates in audit | ✅ Performance API |

Sources: Map Ranks 2026 GBP guide; Revved Digital 2025; Spokk 2025; Google `localPosts.create`
docs; "GBP API 2026 what still works" (slashpost); Q&A API discontinuation (ppc.land).

## Access provisioning — how Dan gets us API access (the part Kody asked about)

GBP write access needs **two** things: (a) our GCP project allow-listed for the Business Profile
API, and (b) our Google account holding a role on the customer's location.

1. **One-time (us):** apply for **Business Profile API access** for our GCP project (allowlist +
   quota). Use a **dedicated ops Google account** as the API identity — e.g. `gbp-ops@practicerank.ai`
   (preferred) or Kody's `kody@l2investing.com` for the pilot. OAuth that account into the project;
   store the refresh token in `secrets` (per-agency, not per-customer).
2. **Per customer (Dan's onboarding step):** Dan asks the customer to add **our ops Google account
   as a *Manager*** (NOT Owner) on their Google Business Profile — Business Profile → Settings →
   People & access → Add → *Manager* → `gbp-ops@practicerank.ai`. Manager can post, edit info,
   reply to reviews, upload photos — everything we need — without owning the listing.
   - Why Manager not Owner: the client keeps ownership/control; we can be removed anytime; lower trust barrier.
3. **Verification:** after the customer adds us, our project can `accounts.locations.list` and the
   location shows up under our ops account → store `location_id` (resource name) on the customer.
   Add a **"GBP access verified"** auto-detected checklist item (green when the location resolves
   via API, like the other auto-detected tasks in `_get_seo_tasks`).

**Onboarding checklist additions** (in the existing `add(key, task, …)` onboarding-task system):
- `gbp_manager_access` — "Customer added gbp-ops@practicerank.ai as Manager on their Google Business
  Profile" with a per-platform guide string + the verification auto-check.
- `client_approval_mode` — set per customer: `dan_only` (we ship on Dan's approval) or
  `client_review` (send the portal link) + auto-approve window. Drives the Stage-2 behavior below.

## Architecture

### `geo_agent/gbp_client.py` (new, thin)
Wraps the GBP APIs we use. Methods: `list_locations()`, `create_post(location, post)`,
`upload_photo(location, media)`, `list_new_reviews(location, since)`, `reply_review(review, text)`,
`get_performance(location, range)`, `update_info(location, patch)`. Auth via the agency ops
refresh token from `secrets`. All write calls **fail safe** (log + surface to Dan, never crash the run).

### Monthly run integration (`geo_agent/main.py` monthly job)
Extend the existing per-customer monthly run to also produce a **`gbp_package`**:
1. Generate **1 post** + **photo selections** from the existing content engine (reuse
   `content_recommender` style prompts, GBP-post-shaped: ≤1500 chars, 1 CTA, keyword + city).
2. **Gate with `validate_html_claims`** — no superlatives, no fabricated credentials, no
   absolutes/future dates. Same guardrail module we just shipped. Block on findings.
3. Draft **review replies** for new reviews since last run (Claude, brand voice, no PHI, no
   review-gating). Status = `pending_approval`.
4. Pull **Performance** metrics → store for the monthly report + feed the worker audit (replace
   some Places-only estimates).
5. Persist everything as **`pending_approval`** GBP items keyed to the customer + month. Nothing
   posts until Dan approves.

### Guardrails carried over
- `validate_html_claims` on every post + review reply (YMYL-safe).
- Review replies: never gate reviews, no incentives, no PHI, "we take feedback seriously" tone.
- Multi-location: per-location packages.

## Dan's admin loop (the approval + checklist part)

New admin surface **"GBP — <month>"** per customer (sibling to the `/fatjoe` queue and content
approval). For each customer Dan sees a **monthly GBP card**:

| Sub-task | Type | Dan's action |
|---|---|---|
| Post draft | auto-generated | Review copy/CTA/image → **Approve** (→ `localPosts.create`) / Edit / Skip |
| Photos (3–5) | auto-selected | Approve set → `media.create` |
| Review replies (N) | auto-drafted | Approve each (or bulk) → `reviews.reply` |
| **Q&A check** | **manual** | Open the listing, seed/answer owner Q&A, tick **done** (API gone) |
| Info accuracy | semi-auto | Confirm hours/holidays/services correct; push edits if needed |
| Performance | auto | Just reviewed → included in the monthly report |

- Model these as a **recurring monthly checklist** (extend `SEO_GEO_TASKS` with a `recurrence:
  "monthly"` flag + a `gbp` category, OR a parallel `GBP_MONTHLY_TASKS`), surfaced through the same
  `_get_seo_tasks` rendering Dan already uses. Auto-detected items (post pushed, photos pushed,
  performance pulled) flip green automatically; manual items (Q&A) Dan ticks.
- **What Dan approves:** every outbound write (post, photos, each review reply, info edits). Nothing
  hits the customer's live GBP without an explicit Dan approval — same posture as content publishing.
- **Tier-aware cadence:** fold GBP volume into `fatjoe_plan.TIER_PLANS` (e.g. Starter = 1 post +
  3 photos/mo; Dominate = weekly posts + 5 photos + priority review replies). Dan's monthly queue
  then shows the right GBP workload per tier alongside the FATJOE link/citation orders.

## Two-stage approval: Dan QA → optional client portal (reusable, NOT GBP-only)

Approval is **two gates**, and the second is a reusable client portal that covers **every monthly
change type** — blog posts, on-site content edits, schema, AND GBP posts/photos/review-replies —
not just GBP. This is the "make it robust" piece.

**Stage 1 — Dan QA (always).** Dan reviews every auto-generated item in the admin app (the GBP card
above + the existing content-approval flow). Dan approves → item becomes `dan_approved`. Nothing is
ever client-visible or live without this. Dan is our quality gate; the client never sees raw model output.

**Stage 2 — Client portal (per-customer, opt-in).** For customers who want a say, Dan's approval
ships the batch to a **login-free client approval link**, modeled exactly on the weekly report
(`/r/<token>` at `dashboard/app.py:1146` — unguessable per-record bearer token, no PHI, revoke by
regenerating; reuse `itsdangerous.URLSafeSerializer` already in app.py for the per-item approve/reject
actions). New route family: **`/approve/<token>`**.
- The client sees a **monthly "Here's what we'd like to publish for you"** page: blog post(s) with
  preview, content changes (diff/preview), GBP post + photos (rendered as they'll appear), drafted
  review replies, info edits. Each item has **Approve / Request change**, plus **Approve all**.
- **Per-customer `client_approval_mode`:** `dan_only` (we ship on Dan's approval — default for
  hands-off clients) | `client_review` (send the portal link, wait for client). "If they want" =
  this setting, set at onboarding and flippable.
- **Auto-approve fallback:** in `client_review` mode, if the client doesn't act within **N days**
  (default 5), Dan-approved items auto-publish so cadence never stalls — with an email warning at
  day 3. Configurable per customer; a cautious client can set "never auto-publish."
- **Audit trail:** who approved (Dan / client / auto), when, what changed — stored per item, shown
  in admin. Same token-security model + `Cache-Control: no-store` as the public report.

**State machine per item:** `generated → (validate_html_claims gate) → pending_dan → dan_approved →
[dan_only: queued_to_publish] | [client_review: pending_client → client_approved / change_requested
→ queued_to_publish] → published`. A `change_requested` kicks back to Dan with the client's note.

**Why reuse, not rebuild:** the content-recommendation approval (`/api/content/approve-all`,
`download-all-approved`) and the report link already model "items with status + a tokenized client
view." The portal is the same primitive generalized: **one approval surface, one token scheme, all
change types** (content + GBP). Build it once here; content publishing adopts it too.

## Customer email campaign (the parts only the client can do)

Some GBP work needs the customer (review velocity comes from THEIR patients; Q&A is manual). Add a
**monthly customer email** (n8n/Resend, same stack as lead notifications):
0. **"Approve this month's work"** — for `client_review` customers, the monthly email's primary CTA
   is the **`/approve/<token>` portal link** (blog posts, content, GBP — all in one place).
1. **"Reply to your new reviews"** reminder — actually, we draft+post replies for them, so this
   becomes **"We replied to N new reviews this month — here they are; forward this review link to
   recent happy patients"** (drives review *velocity*, the ranking factor we can't fake).
2. **"Answer these GBP questions"** — surface new owner-Q&A questions (we detect them in Dan's
   check) and ask the customer to answer, since the API can't.
3. **Review-request nudge** — ties into the parked `specs/platform/review-request-automation.md`.
Track opens/clicks; escalate to Dan if a customer ignores Q&A for 2+ months.

## Phasing

- **M1 — Access + read-only (pilot: Paradigm).** Apply for API access; ops Google account; Dan adds
  us as Manager on Paradigm; `gbp_client` read paths (locations, reviews, performance); verify
  end-to-end. No writes yet.
- **M2 — Posts + photos with Dan approval.** `create_post`/`media.create`; monthly generation +
  `validate_html_claims` gate; Dan approval card; push on approve. Pilot on 1–2 customers (`dan_only`).
- **M3 — Client approval portal (reusable).** `/approve/<token>` built on the `/r/<token>` +
  `itsdangerous` primitives; per-item Approve / Request change / Approve all; `client_approval_mode`
  + N-day auto-approve fallback + audit trail. **Wire BOTH GBP items and existing content/blog recs
  through it** (one portal, all change types). This is the "robust" core.
- **M4 — Review replies + info edits.** Drafted replies, Dan-approved → portal; info-accuracy push.
- **M5 — Email campaign + Q&A checklist + tier cadence + report integration.** Monthly email links
  to the portal; Q&A manual checklist; GBP volume in `TIER_PLANS`; Performance into report/audit.
  Roll to all customers.

## Risks
- **API access approval** can take time and Google can deny/limit — M1 de-risks this first.
- **Q&A is manual** — must not be silently dropped; it's an explicit Dan checklist item + customer email.
- **Posting bad copy to a live customer listing** is outward-facing — hence `validate_html_claims`
  gate + mandatory Dan approval on every write.
- Manager-access can be revoked by the client; handle 403s gracefully and re-prompt onboarding.
