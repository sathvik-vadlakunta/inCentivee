SPEC · PLATFORM

Local Relevancy Engine

One automated monthly module, run per customer and tailored to each customer's domain + business type, that drives the verified local-relevancy levers (citations/NAP, directory breadth, service-area content, review recency, GBP completeness) — the signals our research proved move both Google local-pack rank and AI local recommendations. Everything flows into the PracticeRank Score and the weekly report.

Owner: Kody · Builds on specs/active/lever-b-citations-nap.html · grounded in docs/Local-AI-Search-Playbook.docx + research-review-local-lens.html · 2026-06-18

Why this, why now (verified)

  • The proven local levers are relevancy signals, not backlinks. National digital-PR/earned-mention tactics (Lever A) were national-skewed and unproven for local; what the evidence supports for local is GBP + citations/NAP + reviews + local on-site content + broad third-party directory presence.
  • 3-pack rank ≠ AI recommendation. AI local packs surface only ~32% as many businesses as Google's 3-pack, and AI cites directories/Yelp heavily — so broad, consistent local directory presence is the lever that wins both channels.
  • All five levers are API-automatable and inherently local (per-domain NAP, per-city pages, per-vertical directories) — ideal for our "automate 85%" model.

Canonical NAP rule: pick ONE format (the GBP-verified name/address/phone) and store it as the customer's canonical NAP. Every Module-1 directory check compares against it; every generated page renders it identically. Inconsistent NAP is the #1 thing that tanks local trust (verified: 11/13 errored citations → 28/100).

⭐ Per-business-type directory + signal profiles

The crux of "tailored to each customer." A DIRECTORY_PROFILES map keyed by business_type (falling back to the vertical, then a universal set). Dental and medical both map to the practice vertical but get distinct directory sets — that distinction lives here, finer-grained than vertical_for().

The five modules

Module 1 — Citation / NAP audit + fix build first · scaffold exists

  • Finish brightlocal_client.track_citations() against a live account; confirm the v4 Citation Tracker endpoint + fields (TODO in the file). Per customer = one BrightLocal location, stored as the brightlocal integration's location_id.
  • Seed the customer's BrightLocal location targets from its directory profile (above). Audit each: listed? NAP matches canonical? URL correct? → write to citations.
  • Auto-fix via BrightLocal Citation Builder where supported; queue manual-fix tasks (VA) for the rest into the checklist/todos.
  • Feeds: GEO Foundation pillar (NAP-consistency component) + report "Local listings" section (already built — confirm it lights up once configured).
  • Full detail: specs/active/lever-b-citations-nap.html.

Module 2 — Directory-breadth tracking new (thin)

  • From the same citations data, compute breadth = correctly-listed count ÷ profile target count. This is the verified "broad third-party presence" lever AI uses for local.
  • Feeds: report "broad presence" stat + a GEO-Foundation sub-signal. No new storage — it's an aggregation over citations.

Module 3 — Service-area / nearby-city page generation new

  • NEW helper geo_agent/nearby_cities.py: geocode the customer's city (free Nominatim / or Google Geocoding if keyed), find towns within ~25-min drive (radius heuristic ≈ 15–20 mi, or a drive-time matrix if available), rank by population, cap at N (e.g. 8). Persist to customers.service_areas if empty.
  • Feed nearby cities + the customer's services/procedures into the existing content recommender → generate {service} in {city} pages with the vertical's local schema (table above). Push via the existing staging → CMS-publish flow (human-approve gate stays).
  • Guard against thin/duplicate pages: each page needs unique local context (directions, neighborhoods, local FAQ) — not templated boilerplate.
  • Feeds: Content pillar + the AI city-coverage check (so the new city pages get checked in the AI-mention runs — closes the gap where we added city links but didn't verify them).

Module 4 — Review-recency motion new

  • Verified targets: ~10+ native Google reviews with text, then a steady recent drip (74% of consumers want reviews <3 months old). Track count, rating, and recency from the existing Google Places pull.
  • Automate review requests: generate per-customer review-request copy + the GBP review short-link; surface a monthly "request N reviews" task (or wire to Grade.us if/when configured). Detect staleness (no review in 60–90 days) → flag.
  • Do not score on debunked signals (review velocity > count, keyword-stuffed reviews, 3-week-gap penalty).
  • Feeds: Reputation pillar (rating + recency) + report reviews section.

Module 5 — GBP completeness check new

  • Audit GBP: correct primary category + ~4 relevant additional categories (from the profile), services, hours, attributes, service-area set, photos present. Output recommendations, not vanity tasks.
  • Explicitly exclude debunked "ranking" tactics (geo-tagged photos, post/Q&A quantity, keyword review-responses) — frame those as conversion aids if surfaced at all.
  • Feeds: GEO Foundation pillar + checklist items.

Orchestration

geo_agent/local_relevancy.py
  run_local_relevancy(db, customer_id):
    cust = db.get_customer(customer_id)
    if vertical_for(cust.business_type) not in LOCAL_VERTICALS:
        log("non-local vertical — skipping"); return
    profile = directory_profile(cust.business_type)      # per-business-type
    nap     = canonical_nap(cust)                          # single source of truth
    m1 = citations_audit_fix(db, cust, profile, nap)       # Module 1 (BrightLocal)
    m2 = directory_breadth(db, cust, profile)              # Module 2
    m3 = generate_service_area_pages(db, cust, profile)    # Module 3 (-> staging)
    m4 = review_recency_motion(db, cust)                   # Module 4
    m5 = gbp_completeness(db, cust, profile)               # Module 5
    recompute_score(db, customer_id)                       # pillars refresh
    return summary(m1..m5)

scripts/monthly_local_relevancy.py  --all --stagger        # cron, 1×/month
  - staggered per customer (avoid API bursts, like the AI-check runner)
  - --customer <id> for a single run; respects existing no-email rule
  - writes a weekly-report snapshot so progress shows up

Cron cadence: monthly for citations/GBP (slow-moving), but review-recency + new-city checks can ride the existing weekly cadence. Stagger customers (reuse the AI-check stagger pattern) so BrightLocal/geocode APIs aren't bursted.

  • NEW DIRECTORY_PROFILES config (code-level dict, keyed by business_type) — no migration.
  • NEW customers.canonical_nap (JSON: name/address/phone/url) — small ALTER, defaults derived from GBP.
  • NEW optional local_relevancy_runs (customer_id, ts, module summaries) for history — or reuse the report-snapshot mechanism.

Build phases & acceptance

  1. Phase 1 — Module 1 (Lever B) live. Finish BrightLocal wiring against a real account for one pilot customer per vertical (one dental, one legal, one local_retail). Accept: citations populates, report "Local listings" lights up, GEO Foundation reflects NAP consistency.
  2. Phase 2 — Directory profiles + Module 2. Add DIRECTORY_PROFILES for dental/medical/legal/local_retail/professional_services/default; breadth stat in report. Accept: each vertical audits against its correct directory set.
  3. Phase 3 — Module 3 (nearby-cities + content). Build nearby_cities.py; generate city×service pages into staging with correct vertical schema; feed new cities into AI-mention checks. Accept: ≥1 reviewed city page published per pilot; AI checks cover the new cities.
  4. Phase 4 — Modules 4 + 5. Review-recency motion + GBP completeness audit into Reputation/Foundation + checklist. Accept: stale-review flag fires; GBP category gaps surface.
  5. Phase 5 — Orchestrate. local_relevancy.py + monthly_local_relevancy.py --all --stagger cron; per-run report snapshot. Accept: one monthly run updates score + report for all local customers without manual steps.
Net: we redirect the (unproven, national) Lever-A spend into the proven, automatable, hyper-local stack. Each customer's engine is shaped by its own domain, business type, city, and service area — dental/medical/legal/retail each hit the directories and content schema that actually matter for them.

Open decisions

  • BrightLocal vs Moz Local for Citation Builder auto-push (Lever-B spec leans BrightLocal — confirm account tier covers Citation Builder, not just Tracker).
  • Geocoding source for nearby-cities: free Nominatim (rate-limited) vs Google Geocoding (keyed, we have PAGESPEED_API_KEY-style keys) vs a static metro→towns table.
  • Review-request channel: built-in task + GBP short-link now, Grade.us later (per the tech-stack plan).
  • Medical insurance-directory listings often need manual/credentialed submission — likely a VA task, not API.
