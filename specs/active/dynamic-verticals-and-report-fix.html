Dynamic Vertical Support + Legal/Medical Report Fix

Status: Implemented  |  Priority: P1  |  Created: June 5, 2026  |  Implemented: June 5, 2026

Problem Summary: PracticeRank serves multiple industries (dental, legal, medical, jewelry, etc.) but competitor discovery and report generation are hardcoded for 3 verticals. Dental works well. Legal and medical reports from practicerank.ai landing pages are inconsistent — wrong competitors, false rejections, and missing industry-specific context.

Issue 1: Competitor Discovery Not Dynamic

Current State

Three separate systems discover competitors, each with different limitations:

SystemFileIssue
CF Worker (landing page reports) worker/src/index.js Only knows 3 verticals (dental/legal/medical). Uses searchNearby with a single placeType per vertical. No text search fallback. Anything outside these 3 searches for "dentist".
Dashboard onboarding dashboard/app.py Passes business_type to Python google_places.py which has 15 verticals + text search fallback. But the api_lookup route (line 716) does NOT pass business_type — always finds dentists.
Geo Agent pipeline geo_agent/google_places.py Best implementation — 15 verticals, text search fallback via searchText API, website validation. But still hardcoded — new business types require code changes.

Specific Bugs

Bug 1: Worker line 307 — wrong variable name
competitors = await validateCompetitors(competitors, vertical);
Uses raw vertical (user input, could be undefined) instead of validated vert. If vertical is undefined, validateCompetitors falls through to dental keywords, rejecting valid legal/medical competitors.
Bug 2: Worker fetchNearbyCompetitors — no text search fallback
The worker ONLY uses searchNearby with includedTypes: [placeType]. For verticals not in VERTICAL_CONFIG (jewelry, service, etc.), it defaults to "dentist" and returns dental competitors. The Python code solved this with a searchText fallback — the worker needs the same.
Bug 3: Dashboard api_lookup route (line 716) — ignores business_type
comps = fetch_nearby_competitors(verified.lat, verified.lng, name, api_key)
No place_types or text_query passed. Defaults to ["dentist"]. This is the "Detect" button on the add-customer page — it always shows dental competitors regardless of the business type selected.
Bug 4: Medical placeType too narrow
VERTICAL_CONFIG.medical.placeType = "doctor" — only searches for "doctor" type. Misses hospitals, clinics, urgent care, physiotherapy, chiropractic, dermatology offices, etc. The Python side already has ["doctor", "hospital"] but the worker only has "doctor".

Fix 3: Add text search fallback to worker fetchNearbyCompetitors

async function fetchNearbyCompetitors(lat, lng, practiceName, apiKey, vertical = "dental", textQuery = "") {
  const config = VERTICAL_CONFIG[vertical];
  const placeTypes = config?.placeTypes || (config?.placeType ? [config.placeType] : []);

  // If no place types OR text query provided, use text search
  const useTextSearch = textQuery && placeTypes.length === 0;

  let searchUrl, body;
  if (useTextSearch) {
    searchUrl = "https://places.googleapis.com/v1/places:searchText";
    body = {
      textQuery: textQuery,
      locationBias: {
        circle: {
          center: { latitude: lat, longitude: lng },
          radius: 8000.0,
        },
      },
      maxResultCount: 20,
    };
  } else {
    searchUrl = "https://places.googleapis.com/v1/places:searchNearby";
    body = {
      includedTypes: placeTypes.length > 0 ? placeTypes : ["dentist"],
      maxResultCount: 20,
      locationRestriction: {
        circle: {
          center: { latitude: lat, longitude: lng },
          radius: 8000.0,
        },
      },
    };
  }
  // ... rest of function
}

Issue 2: Legal/Medical Landing Page Reports Inconsistent

Symptoms

  • False rejections: Valid law firm websites rejected with "This doesn't appear to be a law firm website" because the site uses formal language without obvious keywords like "attorney" or "law firm" in the first 3000 chars of visible text
  • Wrong competitors: Medical practice reports show dental competitors because placeType: "doctor" is too narrow and misses the actual specialty
  • Generic findings: The audit prompt uses dental-centric language for scoring categories (e.g., "dental keyword targeting" in the content category for ALL verticals)
  • Dental fallback everywhere: When any vertical detection fails, it silently falls back to dental — the user doesn't know why their legal report reads like a dental audit

Root Causes

Root Cause 1: Site detection is too strict for legal/medical
Legal site detection requires 2+ keyword matches from LEGAL_KEYWORDS in visible text. But many law firms use terms like "our practice", "our team", "contact us" without "attorney" or "law firm" in the first 3000 chars. The detection should also check:
- Page title and meta description (often contains "Law" or "Attorney")
- Schema types (Attorney, LegalService, ProfessionalService)
- Domain name (contains "law", "legal", "esq")
- Navigation links (practice areas, case results, attorneys)
Root Cause 2: Medical placeType is singular "doctor"
Google Places "doctor" type misses: hospitals, clinics, physiotherapy, chiropractic, dermatology, orthopedics, urgent care. A dermatology practice searching for "doctor" competitors may get pediatricians and family doctors instead of other dermatologists.
Root Cause 3: No specialty-aware competitor search
A personal injury law firm should find other PI firms, not estate planning attorneys. An orthopedic practice should find other orthopedics, not dermatologists. The current search uses the broad vertical type with no specialty refinement.

// When vertical is "medical", extract the specialty from the site content
// and use it to build a more targeted competitor search

function extractMedicalSpecialty(siteData) {
  const text = (siteData.visibleText || "").toLowerCase();
  const specialties = {
    "dermatology": ["dermatol", "skin", "acne", "eczema", "melanoma"],
    "orthopedics": ["orthoped", "joint", "spine", "sports medicine", "fracture"],
    "cardiology": ["cardiolog", "heart", "cardiovascular", "cardiac"],
    "pediatrics": ["pediatric", "children", "child health"],
    "primary_care": ["primary care", "family medicine", "internal medicine", "general practice"],
    "urgent_care": ["urgent care", "walk-in", "immediate care"],
    "chiropractic": ["chiropract", "spinal adjustment", "spine alignment"],
    "dental": ["dental", "dentist", "orthodont"],  // redirect to dental vertical
  };

  for (const [specialty, keywords] of Object.entries(specialties)) {
    const matches = keywords.filter(kw => text.includes(kw));
    if (matches.length >= 2) return specialty;
  }
  return null;  // generic medical
}

// Use in competitor search:
const specialty = extractMedicalSpecialty(siteData);
if (specialty) {
  // Text search: "dermatologist near Springfield VA" instead of generic "doctor"
  textQuery = `${specialty} near ${city} ${state}`;
}

Fix C: Legal competitor search — use practice area from scraped data

function extractLegalPracticeArea(siteData) {
  const text = (siteData.visibleText || "").toLowerCase();
  const areas = {
    "personal_injury": ["personal injury", "car accident", "truck accident", "slip and fall", "medical malpractice"],
    "family_law": ["family law", "divorce", "child custody", "child support", "adoption"],
    "criminal_defense": ["criminal defense", "dui", "dwi", "drug charge", "felony", "misdemeanor"],
    "estate_planning": ["estate planning", "will", "trust", "probate", "power of attorney"],
    "immigration": ["immigration", "visa", "green card", "deportation", "asylum"],
    "business_law": ["business law", "corporate", "contract", "commercial litigation"],
    "real_estate_law": ["real estate law", "property", "closing", "title"],
  };

  for (const [area, keywords] of Object.entries(areas)) {
    const matches = keywords.filter(kw => text.includes(kw));
    if (matches.length >= 2) return area;
  }
  return null;  // general practice
}

// Use for more targeted competitor search:
const practiceArea = extractLegalPracticeArea(siteData);
if (practiceArea) {
  textQuery = `${practiceArea.replace(/_/g, " ")} lawyer near ${city} ${state}`;
}

Future: Fully Dynamic (No Hardcoding)

Long-term goal: Instead of maintaining hardcoded vertical configs, use the customer's actual specialties/description to dynamically build search queries. The text search fallback already does this — the place type approach should be a first-pass optimization, not the only path.

Pattern:
  1. Try searchNearby with best-guess place types (fast, structured)
  2. If no results OR results look wrong-industry, fall back to searchText with specialty-based query
  3. Validate all results against the customer's actual industry via website content check
This pattern works for ANY business type without requiring code changes per vertical.
